# Offline sync and operational monitoring

## Principles

Facility care continues when the platform or internet is unavailable. The connector initiates outbound connections only and never blocks the clinical transaction on a network call. The platform is not an authoritative replacement for the facility's clinical database. The legacy MediFlow `/api/v1/sync` mechanism is separate; its presence or documentation is not evidence that it is secure, complete or appropriate for clinical exchange. Review the deployed code, enabled models, access controls and migrations before reusing any part.

For the first WP-3 implementation, the product owner selected operational health and enabled package/module metadata only for pharmacy, clinic, hospital and diagnostic installations. Do not send patient, clinical, financial or aggregate activity records under this scope. Package metadata must reflect the individual installation's verified enabled capabilities, rather than assuming every installation has the same modules.

The selected enrollment flow uses a separate, one-time sync enrollment code generated in the Platform and entered by a server administrator; it must not reuse the licensing credential as the sync credential. Failed outbound messages are managed and retried on the local server; the Platform displays failure alerts. The selected initial server implementation target is the Clinic test installation, not the separate MediFlow Server source checkout. These are scope decisions, not evidence that WP-3 has been implemented or approved for production.

### Implementation checkpoint

The Platform has a gated operational-health ingestion endpoint that accepts strictly allowlisted envelopes, checks the exact JSON payload hash, and transactionally stores per-installation sequence and duplicate markers. Clinic has an outbox writer for a licensed installation's enabled modules, version and operational queue counts.

Clinic has a gated single-event connector. It uses HTTPS, a separate encrypted sync credential, time-limited leases, ordered delivery, individual acknowledgement, bounded retries and a persistent failed state. A failed event blocks later sequence numbers and requires an installation administrator's audited retry. Lost responses can be retried against the Platform's duplicate acknowledgement. Heartbeats are scheduled every five minutes and at most one queued event is attempted each minute. Acknowledged local events are eligible for deletion after 30 days; outstanding events are never purged by this task.

An internal, tenant- and account-link-scoped health projection and an installation-administrator retry interface have been added behind independent flags, both disabled by default. The projection uses the older of observed and received time for freshness, so delivering an old backlog does not falsely mark a server online. It labels a server `delayed` after five minutes and `offline` after fifteen; a timestamp more than five minutes in the future is `unknown`. These provisional thresholds assume synchronized clocks and must be reviewed against the eventual heartbeat schedule. Modules are labeled server-reported, not independently verified. Failure and stale-health warnings are shown in the server list when monitoring is enabled.

KernelBridge has a default-off installation-authenticated, signed enrollment challenge endpoint. The Platform issues a ten-minute code for an active linked server, verifies the signed proof against an explicitly configured public key and creates a separate random sync credential. The code is shown once in the server screen. Issuing another code invalidates previous outstanding codes; redeeming it rotates the sync credential while preserving the sequence. A Platform administrator can revoke the sync credential without revoking the server license. Clinic persists the pending code and proof encrypted before redemption and can retry the identical request after a lost response. Proofs remain acceptable for five minutes, so after that the administrator must issue a new code. The Platform's scheduled cleanup deletes expired codes and encrypted recovery responses.

In the Platform organization workspace, users with server-management permission can open **Operational sync** to find activated servers and generate a sync enrollment code. On Clinic, the installation administrator can open **Operational sync** in the sidebar, which links to the enrollment and failed-message controls in Installation Setup. Those controls are visible only when Clinic sync management is enabled. The separate Platform **Servers** screen also retains its sync controls.

The organization overview summarizes the latest reports for active local sync connections on the current approved account link, available only with server-management permission and monitoring enabled. It is not a complete licensed-server inventory and does not recheck current KernelBridge licensing status. Queue totals add the latest usable server-reported snapshots, including delayed or offline reports, and omit unknown reports; they may be stale. Refresh requests a new summary.

For users with license-management permission, the Platform organization **Reports** screen shows a searchable proposed summary format selected from recognized enabled module grants in the last verified MediFlow organization account-link snapshot. An illustrative chart and table contain fixed, explicitly labeled sample counts for some activity fields, dated 1 October, 1 November and 12 November 2026; they are not Clinic data. Inclusive From and To filters sum only those example entries; an empty bound is open-ended and zero means no example entries in the range. Other fields, including stock and staff snapshots, have no sample. Actual values remain unavailable and are not zero or an approved release; definitions and privacy controls still require review. The screen does not request operational health or facility counts. It accepts both current `mediflow.module.*` keys and legacy module keys, with current keys taking precedence. The snapshot can be stale and is not proof of the modules active on any individual Clinic installation; refresh the link from the License screen to reverify it. If the link or recognized grants are unavailable, no plan-specific fields are inferred.

Clinic's installation-administrator **Insight synchronization** page lists proposed aggregate categories filtered by verified enabled modules. It also offers a local-only, on-demand preview of patient registrations, visits, drug charts, admissions, labour episodes, deliveries and postnatal examinations for eligible modules. Admissions use the owner-selected `PatientAdmission` model. Maternity episode, delivery and examination previews use the event's timestamp and include all statuses; labour episodes are distinct from services named labor. The preview is provisional, is not persisted or sent, and is not an approved reporting release. All synchronization controls are disabled: no scheduled aggregate collection, consent persistence, aggregate transport, Platform patient-derived reports or deletion workflow is implemented. Clinical categories require approved definitions, a minimum of five distinct people and protections against inference from overlapping reports and corrections before activation. These proposed insights are separate from the operational-health connector.

Clinic has an isolated daily aggregate calculator for new patient registrations, patient visits, drug charts by creation date, `PatientAdmission` admissions by admission date, labour episodes by onset, deliveries by delivery date and postnatal examinations by examination date. It returns counts only for completed local calendar days with at least five distinct patients; smaller groups, including zero, are suppressed. This calculator is not scheduled or connected to synchronization, and recalculating it does not freeze previously released values. Immutable releases, protection against differencing across dates, categories and corrections, authorization, consent revocation, queued deletion and Platform reporting remain necessary before activating any category.

Clinic's local preview now uses a versioned metric catalog for the source, timestamp, filters, unit and verified module gate, and rechecks the installation's license immediately before calculating. This catalog version is local-preview metadata, not a Platform delivery contract or a disclosure-safe release.

The owner selected approximate reports with a controlled privacy budget and one contribution per patient per metric per day. Clinic can locally preview exact distinct-patient counts alongside its existing event-count preview; these exact previews are not differentially private and are never synchronized. Reports and corrections must remain disabled until a privacy specialist selects and reviews the budget and a complete design covers cross-period and cross-metric composition, contribution bounds, suppression, retry idempotency, and concurrent accounting.

The Clinic Insight synchronization page marks the release **pending privacy review** and lists the unresolved consent, disclosure and delivery work. This status is not a specialist approval and does not provide an aggregate release path.

Clinic also has an isolated, unprovisioned transactional budget-reservation ledger. It is not connected to collection or delivery and does not generate noise or establish a privacy guarantee. Its accounting semantics, provisioning, recovery, production-database concurrency and integration must be reviewed before use; it must not be reset to regain a budget.

The owner requested drug-chart counts for care; consultation services; separate placeholders for all labour services and services in the surgery category; admission counts; services named labor for labour; distinct medicines in stock and total units; laboratory consumables used and remaining; pharmacy transaction counts; registered revenue, expenses, bills and payments by transaction date; and user counts. The two labour-service proposals can overlap, as might surgery-category services depending on the category mapping. They do not represent counts of distinct surgical procedures. Clinic's `docs/OPERATIONAL_SUMMARY_SYNC_IMPLEMENTATION_GUIDE.md` documents candidate sources and unresolved business-definition gaps. Verified fields alone do not approve matching rules, stock units or record-status semantics. These measures remain proposed and disabled until those details and privacy safeguards are resolved.

Before accepting each event, the Platform refreshes the account link and checks the authoritative KernelBridge installation inventory; it rejects inactive servers and fails closed if KernelBridge is unavailable. This is a point-in-time check, not an atomic transaction across services. Availability and KernelBridge rate limits therefore directly affect sync. Machine endpoints are restricted to the existing synthetic-management `local`/`testing` gate; they are not a production deployment interface.

The flags `KERNELBRIDGE_OPERATIONAL_SYNC_PROOF_ENABLED`, `OPERATIONAL_SYNC_ENROLLMENT_ENABLED`, `OPERATIONAL_SYNC_INGESTION_ENABLED`, `OPERATIONAL_SYNC_MONITORING_ENABLED` and `OPERATIONAL_SYNC_MANAGEMENT_ENABLED` and `OPERATIONAL_SYNC_CONNECTOR_ENABLED` remain off by default. Configuration requires a trusted KernelBridge public-key map on the Platform and a Platform API base URL on Clinic. Domains require HTTPS. A separate default-off `OPERATIONAL_SYNC_ALLOW_INSECURE_IP_HTTP` flag on both applications permits HTTP only with a numeric IP and explicit port in local/testing; the Platform also requires the synthetic-management gate. HTTP does not encrypt or authenticate the connection: sync codes, credentials, proofs and health metadata can be observed or modified. Restrict its use to synthetic test data on a trusted network, preferably loopback; the application does not independently verify that an installation or its data is synthetic. Never enable this exception for real deployments. Laravel schedulers must run on both applications, including to remove expired encrypted enrollment responses; use a shared scheduler lock store for multi-node deployments. Clinic's `MEDIFLOW_VERSION` should be explicitly set to the deployed version; otherwise it is reported as `unknown`.

On the current local test installations, the Platform and Clinic sync migrations have been applied and the six sync flags enabled. The Platform's trusted public key was matched to the local KernelBridge signing key. For loopback-only local testing, the HTTP exception is enabled on both applications and Clinic points to `http://127.0.0.1:8000/api/v1`. The Clinic still requires sync enrollment and both Laravel schedulers must run for automatic synchronization. Enabling the Clinic connector before enrollment causes scheduled commands to report errors until enrollment is complete. These local changes do not change the default-off configuration or the machine API's local/testing synthetic-management restriction.

Synthetic tests cover signed-proof verification, encrypted enrollment recovery, remote status checking, duplicate acknowledgements and an in-process cross-application exchange with a simulated lost response. They do not establish a real HTTPS deployment, production MySQL concurrency safety, real restart recovery or production readiness. Reconcile and test cross-service revocation races, storage failures, re-enrollment after a database restore, and longer outages before any production rollout. The existing legacy clinical sync is not part of this connector.

## Durable outbound design

1. A local transaction records an allowlisted change or a reference to a locally authorized extraction in a durable outbox. Write the outbox entry atomically with the source change when the workflow permits; otherwise use a tested reconciliation process so events cannot be silently missed.
2. Each event has stable `event_id`, installation and tenant binding, type/version, per-stream sequence or source version, occurrence time, creation time, data classification and an immutable payload hash. Assign sequence atomically and retain it across restart.
3. Connector batches bounded events over TLS with its own installation credential. It uses exponential backoff with jitter and bounded concurrency; honor rate limits and do not retry permanent validation or authorization failures forever.
4. Platform authenticates and verifies tenant/installation binding, validates limits/schema and persists deduplication marker and event atomically. Same event ID with a different hash is rejected as a security/integrity incident. Acknowledge only after durable commit.
5. Connector marks each item acknowledged individually. Lost responses are safe to retry; a duplicate with the same hash returns the existing result. Acceptance is distinct from downstream delivery.
6. Track pending, transmitting, accepted, rejected, retrying and delivery-complete states with correlation IDs. Dead-lettered items require operator action and an explicit, audited retry.

Maintain ordered streams where ordering matters. Detect gaps, out-of-order arrival, and conflicting versions; quarantine rather than applying unsafe clinical changes. Batch processing must support partial success without discarding failed items. Apply retention, capacity alarms, disk quotas, poison-message handling and reconciliation, including tombstone/amendment handling. Do not silently drop events when storage fills: alert and follow a facility-approved continuity procedure.

## Inbound commands and policy updates

For pilot, use polling with server-authenticated responses and scoped, expiring command IDs. Commands are acknowledgable, idempotent and replay-protected. Permit only reviewed types such as sync configuration, sharing policy refresh and backup request. Never accept arbitrary shell commands or automatically overwrite clinical records. Capture issuance, verification, local execution and outcome separately. A remote action is not complete until local acknowledgement.

## Authorization and revocation when offline

Check sharing authorization at selection, queueing and delivery, not only when the request was first created. Pending clinical data must be quarantined or discarded per approved retention policy if authorization expires or is revoked. For a disconnected facility, revocation cannot reach it immediately; the platform must stop onward deliveries it controls and show propagation as pending until the facility acknowledges the policy. Previously delivered copies cannot be recalled automatically.

## Operational monitoring

Use an allowlist of aggregate, non-identifying metrics: installation version, heartbeat timestamp, queue counts and oldest age, sync success/failure timestamps, backup result and disk capacity. Show timestamps and expected heartbeat interval. Proposed statuses: `online`, `delayed`, `offline`, `unknown`, with thresholds configured by facility and connection profile. Do not expose record contents or identifiers in dashboard logs or alert messages.

## Integration verification

Test outage across process restart and full disk; credential revocation; repeated events and mismatched hashes; race conditions; out-of-order and missing sequence; partial batches; expired grants; retry exhaustion; and reconnect after a prolonged outage. Use synthetic patient data and verify no duplicate clinical delivery or unintended tenant access.
